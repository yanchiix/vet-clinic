# Адендум № 002 до SRS версії 0.1: повний CRUD для сутностей предметної області

Дата: 14.11.2026.

Статус: **PROPOSED** — очікує рішення Human на SPEC-ADDENDUM-GATE (див. [розділ 9](#9-spec-addendum-gate)).

Baseline: [SRS ветеринарної клініки, версія 0.1](SRS_Vet_Clinic_v0.1.tex), статус **APPROVED**, разом з [ADD-001](SRS_Vet_Clinic_v0.1_addendum_001.md).

Тікет: **A02** — «ADD-002: повний CRUD для сутностей і узгодження відповідей OpenAPI» (текст тікета наведено в [розділі 10](#10-тікет-a02)).

## 1. Причина зміни

Під час зовнішнього рев’ю API-контракту 05.11.2026 рецензент (викладач) зауважив:

1. для сутності «тварина» в описі контракту видно лише `POST` і `PATCH`, тож незрозуміло, як отримати або видалити тварину;
2. для **всіх** сутностей мають бути операції Create, Read, Update, Delete;
3. тести й зведені таблиці мають відповідати тому, що написано в YAML.

Аналіз контракту `api/openapi.yaml` версії 0.1.0 показав:

- `GET /pets` і `GET /pets/{petId}` у YAML є, але не були показані у зведеній таблиці операцій;
- частини сутностей бракує операцій Read, Update або Delete (працівник, розклад, рекомендація, направлення, пропозиція змін), а операції Delete немає в жодної сутності;
- немає завершення власного сеансу (виходу);
- smoke-тести очікували HTTP-коди, яких операція не декларує: `422` для `POST /auth/client-sessions` і `401` для більшості захищених операцій.

## 2. Принцип видалення

Фізичне знищення клінічної історії суперечить baseline: REQ-F-031 вимагає зберігати картку, медичну історію та профіль клієнта, а REQ-F-060 прямо замінює видалення медичного запису позначкою «помилковий». Така сама практика прийнята в реальних медичних системах: медичні записи не видаляються (у HL7 FHIR для цього є статус `entered-in-error`), записи з історією деактивуються, а фізично видаляються лише записи, внесені помилково й без наслідків.

Тому ADD-002 визначає три види операції `DELETE`:

| Вид | Коли застосовується | Результат |
|---|---|---|
| **Фізичне видалення помилкового запису** | Запис створено помилково і він не має клінічної чи організаційної історії | `204`; запис зникає, унікальні значення (телефон, логін, мікрочип) звільняються; зберігається слід видалення (REQ-F-086) |
| **Анулювання** | Документ, переданий клієнту, який не можна знищити (направлення) | `204`; документ лишається в історії з позначкою анульованого та причиною |
| **Відмова** | Медичний запис | Завжди `409` з поясненням: використати позначку «помилковий» за REQ-F-060 |

Якщо умови фізичного видалення не виконані, сервер повертає `409` з переліком перешкод, і запис не змінюється. Для реальних випадків залишаються наявні механізми baseline: блокування працівника, смерть і припинення опіки, скасування прийому чи рекомендації.

Для видалення профілю, облікового запису, картки, прийому та рекомендації причина обов’язкова й передається query-параметром `reason`.

Ідентифікатори продовжують нумерацію baseline (REQ-DP-005): наявні REQ, AC і BDD не перенумеровуються й не змінюються.

| REQ-F-082 | Видалення помилково внесеного прийому | Лише адміністратор, з обов’язковою причиною, може видалити прийом, створений адміністратором, якщо статус «Підтверджено», немає медичного запису й історії змін статусу, а звичайний прийом ще не почався. | REQ-F-083 | Заборона фізичного видалення медичного запису | Запит на видалення медичного запису від будь-якої ролі повинен відхилятися з поясненням, що запис позначається помилковим за REQ-F-060. Запис, його версії та вкладення не змінюються. |
| REQ-F-084 | Перегляд, виправлення та анулювання направлень | Клієнт із правом на картку та ветеринари повинні переглядати направлення тварини й окреме направлення; адміністратор їх не отримує. | REQ-F-085 | Перегляд і видалення рекомендації | Окрема рекомендація повинна бути доступна тим самим ролям, що й рекомендації тварини (REQ-F-064, REQ-F-072); адміністратор отримує лише список очікування. ## 4. Критерії прийняття

| AC-ID | Критерій |
|---|---|
| AC-F-075 | Запит із чинним токеном повертає ідентифікатор і роль без пароля та секретів. Після виходу запит із тим самим токеном отримує `401`; інший сеанс того самого користувача залишається чинним. Запит без токена отримує `401`. |
| AC-F-076 | Профіль без пароля, тварин і прийомів видаляється; після цього номер можна використати для нової реєстрації, а старе посилання недійсне. Профіль із твариною або встановленим паролем не видаляється (`409`, перелік перешкод). Без причини запит відхиляється (`400`). Ветеринар і клієнт отримують `403`. |
| AC-F-077 | Адміністратор отримує список і окремий запис без паролів і посилань. Ветеринар отримує власний запис, а чужий — `403`. Неіснуючий запис — `404`. |
| AC-F-078 | Неактивований обліковий запис без пов’язаних даних видаляється, логін стає вільним. Спроба видалити себе, активований запис або запис із розкладом чи прийомами — `409`. |
| AC-F-079 | Картка без історії видаляється, мікрочип стає вільним. Картка з прийомом, медичним записом, рекомендацією, направленням чи позначкою смерті або припинення опіки не видаляється (`409`). |
| AC-F-080 | Автор змінює або відкликає нерозглянуту пропозицію; позначка потреби перевірки знімається після відкликання. Зміна чи відкликання після рішення — `409`. Інший клієнт отримує `403`. |
| AC-F-081 | Адміністратор і сам ветеринар отримують інтервали на дату. Розклад без майбутніх підтверджених прийомів видаляється; за наявності такого прийому — `409` з його ідентифікатором, розклад не змінюється. |
| AC-F-082 | Помилково внесений адміністратором майбутній прийом без історії видаляється, пов’язана рекомендація повертається до списку очікування, якщо стан тварини дозволяє. Проведений, скасований, розпочатий або створений клієнтом прийом не видаляється (`409`). |
| AC-F-083 | `DELETE` медичного запису від будь-якої ролі повертає `409` з кодом `medical_record_deletion_forbidden`; наступний `GET` повертає той самий запис і версії. |
| AC-F-084 | Клієнт і ветеринари отримують направлення; адміністратор — `403`. Виправлення без причини — `400`; не автором — `403`. Після анулювання направлення доступне для перегляду з позначкою й причиною, а зміна чи повторне анулювання — `409`. |
| AC-F-085 | Клієнт отримує власну рекомендацію, включно з домашньою; адміністратор — `403`. Помилкова рекомендація без версій і прийомів видаляється. Скасована, виправлена або пов’язана з прийомом — `409`. |
| AC-F-086 | Після кожного успішного фізичного видалення сховище містить запис із типом, ідентифікатором, автором, часом і причиною; у записі немає імені, телефону та секретів. Після відмови (`409`) запис сліду не створюється. |

### 6.2. Узгодження задекларованих відповідей

Без зміни бізнес-поведінки baseline кожна операція тепер декларує всі HTTP-коди, які може повернути сервер за вже наявними вимогами:

- `401` — для кожної операції з Bearer-доступом (REQ-NF-011, REQ-NF-012);
- `403` — для кожної операції з Bearer-доступом, бо права перевіряються сервером для кожного запиту (REQ-NF-015);
- `404` — для кожної операції з ідентифікатором у шляху;
- `400` — для кожної операції з тілом запиту або параметрами, зокрема `POST /auth/client-sessions` і `POST /auth/staff-sessions`.

Після цього негативні тести очікують лише задекларовані коди; HTTP `422` більше не використовується.

### 6.3. Ресурси без повного CRUD

Повний CRUD не застосовується до ресурсів, що не є збереженими сутностями:

| Ресурс | Чому без CRUD |
|---|---|
| Реєстрація, відновлення пароля, запрошення, зміна номера, відновлення доступу, встановлення пароля (`/auth/...`, `/client-access-recoveries/...`) | Це процеси (дії) з одноразовими кодами й посиланнями, а не сутності; їх читання чи видалення не має предметного змісту і суперечило б REQ-NF-014 |
| Вільні слоти (`GET /appointment-slots`) | Обчислюються з розкладу й прийомів, не зберігаються |
| Список очікування (`GET /recommendations`) | Подання чинних рекомендацій (REQ-F-068) |
| Сеанс | Має Create (вхід), Read і Delete (вихід); оновлення сеансу не передбачене SRS |
| Вкладення медичного запису | Частина версії медичного запису: створюються й вилучаються лише новою версією запису (REQ-F-057–REQ-F-059), видалення заборонене REQ-F-060 |
| Події смерті й припинення опіки | Створюються й виправляються наявними операціями REQ-F-030–REQ-F-033; видалення замінене виправленням із причиною |
